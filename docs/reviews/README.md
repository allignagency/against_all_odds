# AAO native reviews

Replaces the Loox Reviews app ($39.99/mo) with theme-owned code. Nothing about the storefront
should look different: the widget is a transcription of the live Loox widget's own DOM and CSS
(captured 2026-09-18 from `https://loox.io/widget/v-OorfUjQM/reviews/7176149008537`), down to the
star path data, the grey histogram bars, the 2px card radius and the `0 0 3px rgba(0,0,0,.2)` card
shadow. The `[loox]` comments in `assets/aao-reviews.css` mark every value taken verbatim.

The one deliberate difference: Loox painted stars gold (`#EBBF20`). AAO is a strict monochrome
brand, so `--aao-rev-star` defaults to `#111`. Set it back to `#EBBF20` in
`assets/aao-reviews.css` if the gold is wanted.

## Read this first: the catalogue is padded

The harvest looks like 17,993 reviews. It contains **185 distinct ones**.

Loox served a shared "showcase" feed on products that had none of their own, so the same review
set repeats across many handles. Measured on the 2026-09-18 harvest:

| | products | reviews |
| --- | ---: | ---: |
| Display a **shared** set (no reviews of their own) | 251 | 0 genuine |
| Have a review set of **their own** | 11 | 15 |
| No reviews at all | 58 | 0 |
| **Total** | **320** | **185 distinct** |

There are 8 distinct shared sets, not one: 127 products show the same 124-review store-wide feed,
58 show the same 30, 34 show the same 3, and so on. They look like category groupings (hoodies
share a hoodie set, tracksuits a tracksuit set).

pieces:

### The honesty switch

One boolean, at the top of `snippets/aao-reviews-boot.liquid`:

```liquid
assign genuine_only = false
```

Set it to `true` and every product shows only reviews actually written about it. On today's data
that means **11 products with reviews and 251 showing "Be the first to review this product"**.
Moderated submissions that arrive through the new form are genuine by definition, so they always
show in both modes and a product earns its way out of the pool as soon as it gets a real review.

This is a business decision, not a technical one. Worth putting to Alex before the cancellation,
because the padding is the app's behaviour and the store will keep displaying it otherwise.

## Architecture

Each distinct review **set** is stored once and the summary points every handle at the set it
displays. Generated by `docs/reviews/split_reviews.py`:

```
assets/aao-reviews-summary.json      one row per handle, 35.6KB
       avg / count        what the product displays today (parity)
       own_avg / own_count  its genuine, product-specific reviews
       pool               true when it has no reviews of its own
       src                which asset below holds its review list
        -> fetched once per page that renders a rating badge or the widget

assets/aao-reviews-store.json        the store-wide showcase set (124 reviews, 24.8KB)
assets/aao-reviews-set-<hash>.json   the 7 other shared sets (1.7KB - 6.9KB)
assets/aao-reviews-p-<handle>.json   the 11 products with their own reviews (226B - 611B)
assets/aao-rev-<name>.jpg            the 14 review photos, re-hosted off the Loox CDN

        +  https://allign.agency/aao/reviews/approved.json   (VPS, approved since the migration)
        =  what the badges and the widget render
```

A PDP fetches the summary plus exactly one review asset: 60KB at worst, and nothing extra at all
for a product with no reviews (it is absent from the summary, so nothing is requested).

| File | Role |
| --- | --- |
| `assets/aao-reviews-summary.json` | Per-handle index. Generated. |
| `assets/aao-reviews-store.json`, `-set-*.json`, `-p-*.json` | Review lists, one per distinct set. Generated. |
| `assets/aao-rev-*.jpg` | Review photos. Generated (copied). |
| `docs/reviews/split_reviews.py` | Builds all of the above from a harvest. Re-runnable. |
| `assets/aao-reviews.css` | All widget and badge styling. Transcribed from the Loox stylesheet. |
| `assets/aao-reviews.js` | The engine: merge, render, paginate, lightbox, form, JSON-LD. No dependencies. |
| `snippets/aao-reviews-boot.liquid` | Rendered once from `layout/theme.liquid`. Stylesheet, engine, endpoint config, `genuine_only`. |
| `snippets/aao-reviews-widget.liquid` | The PDP widget mount point. Replaces the Loox `loox-dynamic-section` block. |
| `snippets/aao-rating-badge.liquid` | Stars + count badge. Replaces the Loox `loox-rating` block and the hard-coded `.loox-rating` div in `product-card.liquid`. |
| `sections/aao-reviews.liquid` | Section wrapper so the widget can sit below the product, where the Loox app section sat. |

### Photos

All 1,229 photo references in the harvest resolve to **14 unique images** (2.42MB), now theme
assets. `photos[]` in the baked data holds bare asset filenames, not URLs; the engine prefixes
them with the theme's asset directory, which the boot snippet derives from
`'aao-reviews.css' | asset_url`. Keeping filenames rather than baked CDN URLs means the data
survives a theme or store move untouched.

Nothing in the native system references `images.loox.io`. To confirm after any re-harvest:

```bash
grep -rl "loox.io" assets/ ; echo "(no output above = clean)"
```

### Data schema

The **harvest** file (the generator's input) and `approved.json` share one shape:

```json
{
  "generated_at": "ISO-8601",
  "store": "againstallodds.shop",
  "products": {
    "<product_handle>": {
      "product_id": 123,
      "title": "...",
      "avg": 4.8,
      "count": 12,
      "reviews": [
        { "rating": 5, "author": "...", "date": "ISO-8601", "text": "...", "photos": ["url"], "verified": true }
      ]
    }
  }
}
```

The generated assets are that same shape, sliced. `aao-reviews-summary.json` keeps one row per
handle under `products` (`avg`, `count`, `own_avg`, `own_count`, `pool`, `src`); each review-list
asset holds one product entry at the top level. The generator adds two fields the harvest does not
have:

- `own: true/false` on every review - true when that review appears on exactly one handle, i.e. it
  is genuinely about that product. This is what `genuine_only` filters on.
- `photos[]` rewritten from Loox URLs to theme asset filenames.

Per handle the engine concatenates the overlay's reviews onto the baked ones, de-duplicates on
`author|date|text[0:60]`, and recomputes `avg` / `count`. Set `"replace": true` on an overlay
product entry to discard the baked reviews for that handle instead of merging. The badges cannot
de-duplicate (they only have `avg`/`count`, not the list), so they fold the overlay in
arithmetically; a badge can therefore be off by one only if the overlay re-publishes a review that
is already baked in. The widget's count is authoritative.

If `approved.json` is unreachable, 404s, or is not valid JSON, the failure is swallowed and the
baked data still renders. Same for either asset fetch.

### Performance

Product cards render dozens of times per collection page, so `aao-rating-badge.liquid`
server-renders nothing but `<span class="aao-rating" data-handle="...">`. The engine fetches the
35.6KB summary **once** per page and hydrates every badge from that single parsed object. It
returns immediately, fetching nothing at all, on pages that contain no widget and no badge.

A PDP costs the summary plus exactly one review asset: 60KB on the heaviest product, 36KB on a
product whose own set is small, and 36KB on a product with no reviews (nothing extra is requested).
Photos are lazy-loaded and only for reviews actually scrolled to.

One opt-in switch, off by default: `{%- render 'aao-reviews-boot', inline_summary: true -%}` in
`layout/theme.liquid` embeds the summary in every page instead of fetching it, trading ~36KB of
HTML sitewide for one fewer request.

## Approval flow

1. A visitor clicks **Write a review** on a PDP and fills in rating, name, email, review text.
2. The widget POSTs JSON to `https://allign.agency/aao/reviews/submit`:
   ```json
   { "handle": "dreamers-to-believers-t-shirt", "rating": 5, "author": "...", "email": "...", "text": "..." }
   ```
   A hidden honeypot field (`website`) is checked client-side; anything filled in is dropped
   silently. The endpoint should do its own validation and rate limiting.
3. The endpoint replies `{"ok": true}`. Anything else shows a retry message. On success the form
   is replaced with *"Thanks. Your review is pending and will appear once it has been approved."*
4. Someone approves the submission on the VPS.
5. The VPS regenerates `https://allign.agency/aao/reviews/approved.json` containing every approved
   review in the products-map schema. The endpoint must send permissive CORS
   (`Access-Control-Allow-Origin: https://www.againstallodds.shop`, or `*`) on **both** routes, and
   answer the preflight `OPTIONS` on `/submit`.
6. The next PDP or collection page view picks the new review up. No theme deploy needed.

Endpoint URLs are hard-coded in `snippets/aao-reviews-boot.liquid`. Change them there.

## Re-running the harvest

The assets in the theme were generated from a harvest of 17,993 review rows across 320 products,
taken 2026-09-18, plus 14 photos. To refresh them:

```bash
python3 docs/reviews/split_reviews.py path/to/reviews.json --photos path/to/photos-dir
```

`--photos` points at the directory holding `photos-index.json` and the downloaded images; the
script copies them into `assets/` as `aao-rev-<name>.jpg` and rewrites every photo URL in the baked
data to that filename. Omit it and photo URLs are left exactly as the harvest had them, which for a
Loox harvest means they keep pointing at `images.loox.io` - so do not omit it.

The script regroups the data from scratch every run, so a product that gains its first genuine
review simply stops being a pool product. It also deletes generated assets that this run did not
produce (pass `--no-prune` for a partial harvest), recomputes `avg`/`count` from the review lists
rather than trusting the declared values, sorts newest-first, skips products with zero reviews, and
refuses handles or photo names that are not safe as Shopify asset filenames (it warns and lists
them). `--dry-run` reports without writing.

Then:

```bash
shopify theme check
grep -rl "loox.io" assets/            # must return nothing
python3 -c "import json;s=json.load(open('assets/aao-reviews-summary.json'))['products'];print(len(s),'handles,',sum(1 for r in s.values() if not r['pool']),'with genuine reviews')"
```

and open a PDP plus a collection page on a preview theme to confirm the badge counts match what
Loox shows.

Handles are the join key, so a product renamed in Shopify after the harvest loses its reviews until
it is re-harvested. `product_id` is kept in the per-product files as a second key for repair work.

## Before cancelling Loox

- **Export finality.** Loox's export is only available while the subscription is live. The harvest
  and the photos are already captured, but re-check the distinct-review count against the Loox
  dashboard before cancelling - 185 distinct reviews is the number to confirm, not 17,993. Loox
  does not retain data after cancellation.
- **Photos: DONE.** All 14 unique review images are re-hosted as theme assets
  (`assets/aao-rev-*.jpg`, 2.42MB) and the baked data references them by asset filename. Nothing in
  the native system touches `images.loox.io`. Verify with `grep -rl "loox.io" assets/` - it must
  return nothing. Only `approved.json` on the VPS could reintroduce a Loox URL, so keep photo
  handling out of it.
- **The Loox app embed in `config/settings_data.json`** is still present and is handled separately
  (theme settings, not templates). Turn it off in the theme editor's App embeds panel, or the Loox
  script keeps loading until the app is uninstalled.
- **Loox review-request emails.** If Loox was sending post-purchase review requests, that flow
  disappears with the app. Rebuild it in Klaviyo pointing at the PDP's `#aao-reviews` anchor.
- **The padding conversation.** 251 of 262 products display reviews written about something else
  (see "Read this first" at the top). Parity is preserved by default, and `genuine_only` flips it.
  This should be a decision Alex makes knowingly rather than one that survives by inertia, and it
  is easier to raise now than after the app is gone.
- **Google Shopping / rich results.** Re-run the Rich Results Test on a PDP after deploy and
  confirm `AggregateRating` and `Review` are still detected before cancelling.

## SEO note

Liquid cannot parse a JSON asset, so the review text cannot be rendered server-side from the
generated assets. The engine injects the `AggregateRating` / `Review` JSON-LD (capped at 20 review
nodes) and a visually hidden text copy of the reviews into the DOM after load. This is exactly what
Loox does today (`looxAddProductLdJsonSchema()` runs client-side there too), so the swap is not an
SEO regression. If true server-rendered review markup is wanted later, either:

- render the widget with `inline_reviews: true`, which puts that product's reviews in the page
  source (up to ~24KB on the heaviest product), or
- have the generator emit a Liquid snippet with a `case product.handle` block per product.

## Where things are wired

- `layout/theme.liquid` -> `{%- render 'aao-reviews-boot' -%}` before `</body>`.
- `sections/main-product.liquid` -> block types `aao-rating` and `aao-reviews` in the schema.
- `snippets/product-info.liquid` -> `when 'aao-rating'` / `when 'aao-reviews'` in the block case.
- `snippets/product-card.liquid` -> `{%- render 'aao-rating-badge' -%}` where `.loox-rating` was.
- `templates/product.json`, `product.legends.json`, `product.store-wide.json`,
  `product.collection-fight-week.json` -> block `aao_rating` at the old `loox_rating` position, and
  section `173593565665a6d37f` retyped from `apps` to `aao-reviews` so it keeps its place in
  `order`.
